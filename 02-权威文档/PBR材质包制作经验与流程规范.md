# Minecraft 模组 LabPBR / PBR 材质包制作经验与流程规范

本文整理 `Enchanting Infuser`（Minecraft 1.21.1 NeoForge）项目中的制作流程、排错经验和交付规范，适用于使用 Iris 与 LabPBR 光影的模组方块、方块实体和实体纹理。

## 1. 先分清资源包能做什么

资源包可以覆盖模组提供的资源文件，因此适合制作：

- 方块颜色贴图、法线贴图、AO、POM 高度和材质属性贴图；
- 静态 Block Model JSON、Blockstate 和 Item Model；
- 实体纹理及其 PBR 贴图；
- 通过 `_s` A 通道控制的自发光，以及部分光影支持的发光纹理。

资源包不能直接改变 Java 渲染器控制的逻辑，例如：

- 方块实体的自定义动画轨迹；
- 书本开合、旋转、悬浮高度和骨骼结构；
- 动态粒子、能量环或额外的几何部件；
- 模组代码中硬编码的发光或渲染状态。

EMF/ETF 主要面向实体模型和实体纹理。模组自定义的方块实体渲染器不一定会被它们接管，所以使用前必须确认目标对象是否属于兼容的实体模型路径。

## 2. 制作前的素材摸底

### 2.1 解包并建立清单

先从模组 JAR 中提取以下目录：

```text
assets/<modid>/blockstates/
assets/<modid>/models/block/
assets/<modid>/models/item/
assets/<modid>/textures/block/
assets/<modid>/textures/entity/
assets/<modid>/textures/gui/
```

记录每张原图的文件名、尺寸、色彩模式、透明区域和实际引用位置。不要只根据文件名猜测用途；必须在模型和方块状态文件中确认引用关系。

### 2.2 核对模型父级与 UV

模型中的 `parent` 和 `faces.uv` 决定贴图如何投影到方块表面。以附魔台类模型为例，侧面通常不会采样原图的全部纵向区域；原图中从未被 UV 使用的像素不能用来判断游戏内最终外观。

每张贴图至少要检查：

1. 哪些面使用它；
2. 每个面的 UV 范围；
3. 是否存在透明边、动画帧或图集拼接；
4. 普通版和进阶版是否共用构图，只改变某些材料区域。

本项目的关键教训是：侧面原图中存在红色像素，即使这些像素在美术上看起来像“底部装饰”，经过模型 UV 后仍可能成为游戏画面中的底部红毯横带。因此，PBR 通道修正无法替代基础颜色贴图和 UV 审查。

### 2.3 记录材质语义

不要把所有明暗变化直接当作高度。应结合颜色、用途、构图和相邻像素，把区域归为明确材质，例如：

| 材质 | 常见语义 | 处理重点 |
|---|---|---|
| 金属金/铁 | 框架、边条 | 高光滑度、金属预设、边界法线 |
| 红毯/布面 | 软质装饰 | 低光滑度、孔隙率、低高度 |
| 紫色核心 | 宝石或魔法晶体 | 中高高度、适量 SSS 或自发光 |
| 黑曜石 | 底座、深色结构 | 高光滑度、低高度、接触 AO |
| 符文 | 凹刻或能量纹路 | 低高度、凹槽 AO、独立发光 |

## 3. 分辨率与文件命名规范

### 3.1 邻近放大

16×16 原图制作 128×128 PBR 时使用最近邻放大 8 倍，保持每个原始像素对应一个 8×8 区块。不要在第一次放大时使用双线性或 Lanczos，否则会把原版像素边界变成无法控制的渐变。

实体纹理也按相同比例放大。例如 64×32 应输出 512×256。

### 3.2 文件名

PBR 文件必须与基础贴图同名，仅添加后缀：

```text
enchanting_infuser_top.png
enchanting_infuser_top_n.png
enchanting_infuser_top_s.png
```

不要保留源文件名中的 `block_` 前缀，除非基础贴图本身也使用该前缀。Iris 按基础纹理路径寻找同名 `_n` 和 `_s` 文件。

### 3.3 透明区

透明像素的 RGB 应清零。透明区若携带法线、AO 或高光数据，在 mipmap、过滤和斜视采样时会污染可见边缘。

## 4. LabPBR 通道设计

### 4.1 `_n.png`

常用含义如下：

| 通道 | 含义 | 安全起点 |
|---|---|---:|
| R | 法线 X | 128 为平面 |
| G | 法线 Y | 128 为平面；注意目标光影的方向约定 |
| B | AO | 255 为无遮挡，缝隙逐步降低 |
| A | 高度/POM | 255 为最高表面，较低值表示凹陷 |

法线不要直接把普通法线图的蓝色通道当作 LabPBR 的 B 通道。B 是 AO，A 才是高度。

### 4.2 `_s.png`

| 通道 | 含义 | 典型用途 |
|---|---|---|
| R | 光滑度 | 布面低，抛光金属和宝石高 |
| G | F0 或金属预设 | 非金属通常 8–20；金属使用 LabPBR 预设 |
| B | 孔隙率或 SSS | 0–64 为孔隙率，65 以上通常进入 SSS 区间 |
| A | 自发光 | 0–254 表示发光强度，255 常被当作忽略/默认值 |

不同光影对高级通道的解释可能略有差异。交付时应以目标光影实测为准，不能只看通道数值。

推荐金属 G 值：铁 230、金 231、铬 233、铜 234；普通非金属可从 10 开始。

## 5. POM 高度图的制作原则

### 5.1 先做结构平台，再做细节

POM 最容易失败的做法是直接把原图灰度拉伸成高度。原图中的受光和背光只是绘画效果，不一定代表真实几何高度。

更稳定的流程是：

1. 按材质和几何意义建立高度平台；
2. 在不同材质之间保留明确高度差；
3. 只对边界做很窄的柔化；
4. 外轮廓设置为满高；
5. 再从高度差生成法线和 AO。

本项目使用的相对层级示例：

```text
金属金框 1.00
铁框     0.96
紫色核心 0.88
红毯     0.64
普通底材 0.58
黑曜石   0.44
符文     0.12
```

这些数值不是所有材质包的固定标准，而是用于保持结构逻辑的起始值。

### 5.2 边缘安全规则

方块轮廓边缘的 A 通道应接近 255。边缘高度过低时，POM 可能把相邻区域的视差迭代到方块外侧，表现为轮廓参差、漏色或错误拉伸。

透明区不能被“边缘满高”逻辑误伤。正确逻辑是“可见边缘满高，透明区域保持透明且 RGB 为零”。

### 5.3 法线和 AO

法线应由平滑后的高度图生成，再按目标分辨率校准强度。16×16 原图放大到 128×128 后，直接在块内做差分大多会得到平面法线；应在边界生成可控的窄法线，并避免把每个颜色噪声都当成几何起伏。

AO 应重点放在：

- 材质交界处；
- 符文凹槽；
- 底座与上层结构的接触处；
- 凹角和窄缝。

## 6. 自发光设计规范

自发光应按视觉功能分层，而不是整张贴图统一提高 A：

- 符文：强度最高；
- 魔法核心：中等强度；
- 核心边缘或相邻材质：低强度过渡；
- 金属框、红毯、黑曜石底座：默认不发光；
- 进阶版灰色金属：除非原设计明确要求，否则不加入邻接辉光。

发光颜色来自基础颜色贴图，`_s` A 只控制强度。Bloom 是否可见还取决于光影设置，因此应同时检查光影中的 Bloom、Emission 和 POM 选项。

实体书文字若要发光，应先在原始实体纹理中识别文字或高亮区域，再只给这些像素设置 `_s` A；整页统一发光会导致纸张失去层次。

## 7. 实体纹理与书本处理

实体纹理通常不是方块面贴图，不能直接套用 block 的 UV 逻辑。制作步骤：

1. 从实体模型或渲染器确认纹理尺寸和 UV；
2. 按原比例邻近放大；
3. 生成同尺寸 `_n` 和 `_s`；
4. 对纸张、封皮、文字分别设定材质；
5. 在游戏中检查实体渲染器是否实际读取这些同名 PBR 文件。

如果书本由模组自己的方块实体渲染器绘制，资源包可以改变纹理和 PBR，但不能改变开合、旋转、浮动和骨骼动画。要修改这些行为，需要 NeoForge 客户端扩展或注入渲染器。

## 8. 生产流水线建议

推荐将源文件、蒙版、生成脚本和最终资源包分开：

```text
work/src/       原始贴图
work/masks/     材质/几何蒙版
work/out/       普通版本输出
work/out_v2/    旧版视差输出
EnchantingInfuser-PBR-128x-vN/  可解包资源包
EnchantingInfuser-PBR-128x-vN.zip  交付包
```

每次生成都应记录：

- 输入模组版本；
- Minecraft、NeoForge、Iris 和目标光影版本；
- 高度平台和材质通道参数；
- 修改过的基础颜色贴图；
- 已知限制和未完成项目。

脚本应尽量做到确定性生成。不要手工改一张输出图后又用脚本覆盖，避免源文件、蒙版和最终结果不一致。

## 9. 交付前检查清单

### 资源路径

- [ ] 命名空间与模组 `modid` 一致；
- [ ] 基础贴图与 `_n/_s` 同名；
- [ ] block、entity、item 路径与模组引用一致；
- [ ] ZIP 内使用正斜杠 `/`；
- [ ] ZIP 根目录直接包含 `pack.mcmeta` 和 `assets/`。

### 图片质量

- [ ] 16×16 方块 PBR 为 128×128；
- [ ] 64×32 实体纹理 PBR 为 512×256；
- [ ] 透明区 RGB 为零；
- [ ] `_n` 的 R/G 不是整张贴图固定 127/128；
- [ ] `_n` 的 B 确实是 AO，A 确实是高度；
- [ ] 金属区域 `_s` G 使用金属预设；
- [ ] 发光区域只覆盖符文、核心或文字；
- [ ] 侧面 UV 实际采样区域没有错误红色、紫色或透明泄漏。

### 游戏验证

- [ ] 单独启用当前版本资源包，关闭旧版本；
- [ ] 用 `F3+T` 重载后仍能正确显示；
- [ ] Iris 已启用并选择支持 LabPBR 的光影；
- [ ] POM/Parallax 和 Bloom 按需开启；
- [ ] 近距离检查顶面、侧面、底面和进阶版；
- [ ] 斜视检查方块轮廓是否出现视差越界；
- [ ] 检查实体书文字、封皮和发光强度；
- [ ] 必要时完全重启游戏，排除启动时缓存或配置未重读的问题。

## 10. 常见问题与定位顺序

### 看不到 PBR

按以下顺序检查：资源包是否启用、资源包优先级、Iris 是否启用、光影是否支持 LabPBR、光影是否在启动时读取到正确配置、贴图是否与基础纹理同名。

### 底部出现不该有的红色

先看基础颜色贴图和模型 UV，再看 `_s`。如果原始侧面纹理的采样区域包含红毯色块，修改粗糙度或金属度不会消除红色。应针对实际采样区域修正基础颜色，并同步调整高度和材质分类。

### POM 看起来像普通平面

检查高度 A 是否几乎集中在 224–255；如果是，说明高度层级过浅。应重新建立材质平台，增加符文、底材和核心之间的高度差，并确认光影的 POM 选项已开启。

### 画面边缘出现彩色污染

检查透明区 RGB、side 顶部未采样区域、mipmap 和方块轮廓高度。透明像素不能携带正常材质的 RGB 或高度数据。

### 进阶版发光过脏

普通版和进阶版不能盲目共用所有辉光规则。进阶版灰色铁框应使用铁金属属性；只有明确的核心或符文区域发光，邻接辉光应降到很低或关闭。

## 11. 推荐的版本管理方式

每个可测试版本使用独立目录和 ZIP，例如：

```text
EnchantingInfuser-PBR-128x-v3.zip  分层 POM
EnchantingInfuser-PBR-128x-v4.zip  加入核心与符文发光
EnchantingInfuser-PBR-128x-v5.zip  修正侧面/底部误显示、书页文字发光
```

版本号变化时同步更新 `pack.mcmeta` 描述，并在工作日志中写明“基础颜色是否修改”“PBR 参数是否修改”“是否需要重启游戏”。这样可以快速判断画面变化来自资源包、光影参数还是游戏缓存。

## 12. 本项目的最终经验

PBR 制作不是单独绘制 `_n` 和 `_s` 两张图，而是“原始贴图、模型 UV、材质语义、POM 高度、光影支持和游戏缓存”共同决定的渲染链。出现错误颜色时先查基础纹理和 UV，出现平面效果时再查高度与光影设置，出现脏边时检查透明区和轮廓高度。只有把这几层分开验证，才能稳定地定位问题并复现结果。

## 附：资源包必须声明 LabPBR 格式（跨光影视差错乱的根因）

`_n` / `_s` 的通道含义在 **labPBR** 与 **oldPBR（seusPBR）** 下不同。资源包若不声明自己用 labPBR，
部分光影会按 oldPBR 解码，造成通道错位：

| 通道 | labPBR（本包语义） | oldPBR（被误判） | 后果 |
|---|---|---|---|
| `_n` B | 材质 AO | 法线 Z 分量 | 法线归一化后严重倾斜 → 光照 / 视差视觉错乱 |
| `_s` G | F0 / 硬编码金属(230+) | 金属度 0–255 | 反射性质整体改变 |
| `_s` B | 孔隙率 / SSS | 自发光 | 大面积假发光 |
| `_s` A | 自发光 | 未使用 | 真自发光丢失 |

**修复**：每个包都必须在 `assets/minecraft/optifine/texture.properties` 写入一行：

```properties
format=lab-pbr/1.3
```

声明后 Iris 会定义 `MC_TEXTURE_FORMAT_LAB_PBR` 与 `MC_TEXTURE_FORMAT_LAB_PBR_1_3` 宏，
光影才会走 labPBR 解码路径。**目前唯一受支持的 labPBR 版本就是 1.3**，不要写其他版本号。

注意事项：

- 不支持 labPBR 的光影（SEUS PTGI 系列等）无论如何都按 oldPBR 解析，需另出一套 oldPBR 包。
- 光影侧若有 RP Support / PBR Format 选项，要选 **LabPBR**（BSL 里的 "Old PBR + Emissive" 是 oldPBR，不要选）。
- 三个项目的生成脚本均会输出该文件：`work/scripts/restore_enchanting_side_v7.py`（附魔灌注台 v7）、
  `work/gen_projecte_armor_table_v4.py`（ProjectE v4）、`work_tlm/gen_tlm_pbr_v3.py`（车万女仆 v3）。
